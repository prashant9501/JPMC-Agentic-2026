🏗️Part 1

RAG Foundations — Why, What, When

🔗From Deck 1 to Deck 2: Where We Are

Where Deck 1 Left Us

We built the foundation: embeddings turn meaning into vectors, vector DBs let us search those vectors in milliseconds across millions of documents, and hybrid search beats pure semantic. We also saw why long-context LLMs aren't a substitute for retrieval — context rot, lost-in-the-middle, and distractor interference all degrade quality before the window fills.

What is RAG?

Retrieval-Augmented Generation (RAG) is a pattern where, before asking an LLM to generate an answer, we retrieve relevant context from an external knowledge source (vector DB, search index, graph, API) and inject it into the prompt.

Retrieve → Augment → Generate

The One-Sentence Definition

"Give the LLM open-book access to the right reference material at the moment of answering, rather than relying on what it memorized during training."

Why This Pattern Matters

RAG converts an LLM from a "know-everything-but-sometimes-confabulate" oracle into a research analyst with reliable sources. The LLM provides reasoning and language fluency; retrieval provides the facts. Each does what it's best at.

The shift in mental model: instead of asking "how do I get a bigger / smarter model?", we ask "how do I get the right context in front of any decent model?" That second question is much more tractable — and much cheaper to iterate on.

🎯The Three Problems RAG Solves

❌ Problem 1: Hallucination

LLMs confidently generate plausible-sounding facts that are wrong. Particularly dangerous for BFSI — a fabricated regulation citation can cost crores in compliance fines.

Banking example: Asked for "Section 17.3 of FEMA limit", the model invents a number that sounds right but isn't in the actual circular.

❌ Problem 2: Stale Knowledge

Training data has a cutoff. Today's RBI Master Direction, this week's market data, yesterday's customer transactions — the model literally doesn't know.

Banking example: "Latest digital lending guidelines" — fully published last month, but the model has no idea they exist.

❌ Problem 3: Private & Proprietary Data

Your bank's internal policies, customer records, product specifics, deal pipelines — none of it is in the model's training data, and you can't put it there.

Banking example: "What's our internal limit for cross-border NRI transfers under FEMA Form A2?"

How RAG Solves All Three

Problem RAG's Answer
Hallucination Ground every answer in retrieved passages. The LLM cites where it got facts. Easy to audit, easy to verify.
Stale knowledge Update the knowledge base — no model retraining. New circular published Monday? Index it Monday. Queries Tuesday onwards know it.
Private & proprietary data Keep your data in your vector DB, in your VPC. The LLM only sees what you retrieve at query time — and only for that query.

Bonus benefit: RAG also reduces cost. A focused 5K-token prompt with 5 retrieved chunks is 100× cheaper than dumping a 500K-token corpus into context — and produces better answers (as Deck 1 established).

Empirical impact: RAG reduces hallucination rates by up to 71% when properly implemented and evaluated (synthesis from production deployments, 2025-26).

🛑When RAG Is NOT the Right Tool

RAG is powerful — but it's not a hammer for every nail. Knowing when not to use it saves time and tokens.

Scenario Why RAG Is Wrong What To Use Instead
Need to change the model's style, tone, or format RAG injects facts. It doesn't teach the model to write differently. Fine-tuning or prompt engineering with system prompts & examples
Domain has specialized vocabulary the model doesn't understand at all (e.g., dense Sanskrit-style legalese) Retrieving more of the same language won't help if the model can't process it Continued pre-training or domain-specific fine-tuning
You need answers to computational questions (math, code execution, SQL aggregates) The answer isn't in any document — it requires running code Tool-use / function calling (code interpreter, SQL agent)
Tiny knowledge base that easily fits in 10-20K tokens RAG infrastructure overhead isn't worth it Just put it in the system prompt; use prompt caching for cost
Knowledge changes too fast to index (e.g., live tick data) Index lag makes RAG always stale Live tool / API call at query time (Tavily, Brave, exchange APIs)
The user needs reasoning over a single long document from start to finish (e.g., contract review) Chunking can break the logical flow; you actually want full context Long-context LLM for the whole doc — or map-reduce over chunks
Use case requires strict determinism (regulatory output must be byte-identical) LLMs are not deterministic even with temperature=0 Template-based generation with rules; LLM only for natural-language polish

The general rule: RAG is the right tool when you need the LLM to answer questions about a body of knowledge that is large, changing, or proprietary. For everything else — explore other tools first.

⚖️RAG vs Fine-Tuning vs Long-Context Window

These three approaches solve overlapping problems but with different strengths. Most production systems use more than one — they're complements, not substitutes.

Dimension 🔍 RAG 🎯 Fine-tuning 📜 Long-Context
Adds factual knowledge? ✅ Yes (best for this) ⚠️ Possible but inefficient ✅ Yes (but degraded — see context rot)
Changes style / format / behavior? ⚠️ Partial (via prompt) ✅ Yes (best for this) ⚠️ Via few-shot examples
Knowledge freshness ✅ Real-time (re-index) ❌ Static (frozen in weights) ✅ Each query is fresh
Source attribution ✅ Yes (built-in) ❌ No ⚠️ With prompting
Hallucination reduction ✅ Strong ⚠️ Mild ⚠️ Moderate (rot kicks in)
Cost to add new knowledge ✅ Low (re-embed chunk) ❌ High (re-train) ⚠️ Pay per query (huge prompts)
Inference latency ⚠️ +retrieval (50-200ms) ✅ Fastest ❌ Slow (large prompts)
Inference cost ✅ Low (focused prompts) ✅ Lowest ❌ Very high (large prompts)
Maintainability ✅ Update KB anytime ❌ Re-train cycles ✅ No infra to maintain

The Decision Rule

  • Need to add knowledge (the most common case in BFSI) → RAG
  • Need to change tone/style/format consistently → Fine-tuning (often layered on top of RAG)
  • Need to reason over a single long document end-to-end → Long-context
  • Need both knowledge AND style consistency → Fine-tune for style, use RAG for facts (production gold standard)

💰What Actually Drives ROI in RAG Projects

In our experience deploying RAG in banks and NBFCs, the projects that deliver have a different shape from those that look impressive in pilots. Here's the gap.

The High-ROI Patterns

  • Internal-facing first. Compliance Q&A, RM enablement, ops support — quality bar is "useful", users can correct mistakes. Much faster path to production than customer-facing.
  • Narrow corpus, deep utility. "Search across all RBI circulars" beats "search across everything we have". Easier to evaluate, easier to improve.
  • Citations + escalation built in. Answer with sources, and an obvious "escalate to expert" button when confidence is low. Wins user trust fast.
  • Replace search, not the human. Frame as "10× faster than browsing the policy portal", not "replaces compliance officer".

The Low-ROI Anti-Patterns

  • "Boil the ocean" knowledge bases. Indexing all 500K docs across the bank → impossible to evaluate; impossible to debug failures.
  • Customer-facing chatbots without strict guardrails. One wrong answer about loan eligibility → reputational + regulatory risk.
  • Demo-driven scoping. Picking 5 cherry-picked questions to dazzle the steering committee. Real usage exposes the gaps.
  • No eval loop. Shipping without RAGAS / DeepEval thresholds → silent quality drift; you only learn when users complain.
  • Skipping retrieval improvements in favor of "bigger model". Going from GPT-4o-mini to Claude 4.5 Opus rarely fixes a retrieval problem. Reranker + hybrid + good chunking does.

The Sequence That Works

  1. Pick a narrow, internal use case with clear users (e.g., "policy Q&A for branch staff")
  2. Build naive RAG with hybrid search (BM25 + vector + RRF) + a reranker — that's it, no fancy techniques yet
  3. Set up RAGAS / DeepEval with 50-100 real queries; establish a baseline (faithfulness, context precision, answer relevancy)
  4. Pilot with 10-20 real users; collect their corrections as training data
  5. Identify failure modes — query rewriting? Chunk size? Then apply the right advanced technique (Part 5).
  6. Roll out gradually; monitor metrics in production

⚙️Part 2

How RAG Actually Works — Step by Step

🏗️The Canonical RAG Architecture

Every production RAG system runs through these eight steps. Some collapse into a framework call, some are explicit components, but they're all there.

The mental model that matters: Phase 1 (Indexing) is a data engineering pipeline — done in batch, can be slow, optimized for thoroughness. Phase 2 (Query) is a real-time pipeline — every millisecond counts, every step must be lean.

📄Steps 1-2: Document Loading & Chunking

Step 1: Document Loading

You need to convert everything in your knowledge base into clean text the embedding model can process. This is messier than it sounds.

Source Loader / Approach Gotchas
PDFs (text-based) PyMuPDF, pdfplumber Tables, multi-column layouts, footnotes break naively
PDFs (scanned) OCR via Tesseract, AWS Textract, GCP Document AI Quality matters — bad OCR ruins downstream RAG
Word / .docx python-docx, unstructured.io Embedded tables, footnotes, tracked changes
Excel / CSV pandas + custom serialization Tables don't embed well — convert to Q&A or markdown rows
HTML / web BeautifulSoup, trafilatura, Playwright (for JS-heavy) Boilerplate (nav, ads) pollutes signal
Slides (.pptx) python-pptx + per-slide treatment Speaker notes often contain the real content
Databases SQL → templated text ("Customer X had Y transactions in Z period") Don't embed raw SQL rows — embed natural-language facts

Step 2: Chunking

Chunking = splitting documents into passages that can each be embedded and retrieved independently. This is one of the highest-leverage decisions in RAG — get it wrong and no amount of advanced retrieval will save you.

The fundamental tension:

  • Smaller chunks = more precise retrieval, but each chunk may lack the surrounding context to be useful
  • Larger chunks = more context, but harder to retrieve precisely; risk of context rot when stuffed into the prompt

✂️Chunking Strategies: The 2026 Landscape

Strategy How It Works Best For Pitfalls
Fixed-size Split every N tokens (e.g., 512), with M-token overlap Quick baseline, dev/testing Cuts across sentences & sections; loses context
Recursive character Try splitting on \n\n, then \n, then ". ", then space — go down the hierarchy Most general-purpose default Still naive about meaning
Semantic chunking Embed sentences; split where adjacent embedding similarity drops below threshold Mixed-topic documents, blog-style content Slower (embedding upfront); needs tuning
Document-structure aware Split at H1/H2 headings, section breaks, page boundaries — respect the doc's own structure Well-structured docs (policies, manuals, RFCs) Needs reliable structure extraction; useless for unstructured text
Sentence-window Embed single sentences; retrieve ± N sentences around the hit at query time Precise retrieval + rich context in prompt Index grows large; need to track windows
Parent-child Embed small "child" chunks; retrieve, then return the larger "parent" chunk to LLM Same problem as sentence-window; cleanly handles hierarchical docs Bookkeeping; choose parent & child sizes thoughtfully
Agentic chunking LLM reads doc, decides where to chunk based on content meaning High-stakes content; small high-value corpora Expensive at scale; only justified for premium content
Late chunking (Jina, 2024) Embed entire long doc, THEN chunk the per-token embeddings Each chunk's embedding reflects full-doc context Needs models with long context; less mature tooling

The Empirical Headline

Optimized semantic chunking achieves 0.79-0.82 faithfulness scores, compared to 0.47-0.51 for naive fixed-size chunking — a roughly 70% relative improvement in production benchmarks.

Faithfulness numbers from 2026 RAG framework benchmarks (Starmorph, Confident AI, RAGAS evaluation reports). "Naive fixed-size" = 512 tokens with 50-token overlap, no structure awareness. "Optimized semantic" = adaptive chunk size + sentence-window retrieval + content-aware splitting.

📏Chunk Size & Overlap: The Numbers

Typical Chunk Sizes (Tokens)

Chunk Size When To Use Notes
~100-200 tokens Sentence-window or parent-child setups; precise lookups Per-chunk precision high; retrieve more chunks (top 10-20)
~300-500 tokens 2026 sweet spot for most docs Balances precision & context; works with most embedding models
~500-800 tokens Dense regulatory / legal text with long sentences Avoids splitting mid-clause; for OpenAI text-3 and similar
1000+ tokens Rarely — only for long-context embedding models (Voyage-3, Cohere v4) Each chunk should still fit comfortably in the model's context window

Overlap Between Chunks

Overlap = repeat the last N tokens of the previous chunk at the start of the next, so a sentence that crosses the boundary appears in both chunks.

  • Typical overlap: 10-20% of chunk size (so ~50-100 tokens for a 500-token chunk)
  • Too little overlap: Key sentence at the chunk boundary gets cut in half — retrieved chunk lacks the full thought
  • Too much overlap: Storage waste; duplicate retrievals; downstream confusion when same content appears in multiple chunks

Practical Recipes for BFSI

Document Type Chunk Size Overlap Strategy
RBI / SEBI circulars 400-600 tokens 15% Document-structure aware (section headers as breakpoints)
Internal policies / SOPs 300-500 tokens 15% Recursive or document-structure
FAQs / customer-support docs One Q&A per chunk None Pre-structured; each pair is naturally atomic
Loan / contract documents 500-800 tokens 20% Document-structure (per clause) + parent-child
Research / analyst reports 500-700 tokens 15% Semantic chunking — themes shift across the report
Long earnings transcripts 300-500 tokens 10% Speaker-turn aware (CFO vs analyst vs CEO)

Don't pick chunk size by gut — evaluate. Pick 50 real user queries with their "ideal" answer passages. Try 3 chunk sizes. Measure context precision & recall (we'll see how in Part 4). Pick the winner.

🧠Steps 3-4: Embedding & Indexing

Both topics covered in depth in Deck 1 — quick consolidation here so the pipeline is complete.

Step 3: Embedding Each Chunk

For each chunk, run it through your embedding model to produce a vector.

  • Model choice (recap from Deck 1): Voyage-3-large or OpenAI text-3 for English RAG, Cohere v4 for multimodal, BGE-M3 for self-hosted multilingual, Gemini Embedding 001 for cutting-edge multimodal
  • Critical rule: the same model must be used for indexing AND querying — different models = different vector spaces
  • Batch the calls: embedding APIs are 10-100× more efficient batched. Process chunks in groups of 32-256.
  • Rate-limit handling: for large corpora (100K+ chunks), build in retry logic and respect API rate limits

Step 4: Indexing (Loading into the Vector DB)

Store the embedded chunks in your chosen vector DB along with metadata.

What goes in alongside each vector:

  • The chunk's original text — needed at query time to give to the LLM
  • Source identifiers — document name, page number, section heading, URL — for citations
  • Filterable metadata — date, department, document type, jurisdiction, sensitivity level
  • Chunk-level metadata — position in document, parent chunk ID (for parent-child setups)
{ "id": "rbi_lrs_2024-25_007_chunk_12", "vector": [0.024, -0.187, 0.451, ...], // 1536 floats "text": "Under the Liberalised Remittance Scheme, resident individuals may remit up to USD 250,000 per financial year for any permissible current or capital account transaction...", "metadata": { "source_doc": "RBI/2024-25/007 - Master Direction on LRS", "section": "3.1.2", "page": 14, "date": "2024-04-15", "jurisdiction": "India", "doc_type": "regulation", "version": "1.3" } }

Beyond the vector DB: build a BM25 index too. If you're using a VDB that supports hybrid (Weaviate, Qdrant, Vespa, OpenSearch), use its built-in BM25. If not, run an external BM25 (rank_bm25 in Python, or Elasticsearch) — you'll need it for hybrid retrieval in Step 6.

🔍Steps 5-6: Query Embedding & Retrieval

Step 5: Query Embedding

The user's query goes through the exact same embedding model used for indexing. The output is a query vector in the same space as your indexed chunks.

  • No preprocessing of the query usually — keep it as-is. Modern embeddings handle casing, punctuation fine.
  • Optional query rewriting — for short / vague queries, you can have an LLM expand them first (more on this in Part 5)
  • Caching: for high-volume identical queries, cache the embedding

Step 6: Retrieval — This Is Where Everything Happens

The retrieval step is the single biggest factor in final answer quality. "Naive RAG" picks top-K by cosine similarity and calls it done. Production RAG runs a multi-stage pipeline.

Naive vs Production Retrieval

Stage Naive RAG Production RAG (2026 standard)
1. First-stage retrieval Vector search only, top 5 Hybrid: BM25 top 50 + Vector top 50
2. Fusion — Reciprocal Rank Fusion (RRF), k=60 → top 100
3. Filtering — Metadata filters (date, jurisdiction, dept) applied
4. Reranking — Cross-encoder reranker scores top 100, picks top 10-20
5. Diversification (optional) — MMR or similar to avoid 5 near-duplicate chunks
6. Final to LLM 5 chunks Top 5-10 highly-relevant, diverse chunks

This pipeline is the single biggest jump from naive to good RAG. Most teams that move from "RAG works in demo, fails in pilot" to "RAG works in production" do so by implementing this pipeline — not by switching to a fancier LLM. Next slide is the picture.

Why This Pipeline Wins

  • BM25 catches the exact-match queries (PAN numbers, IFSC codes, section refs) that pure semantic misses

📝Step 7: Augmentation — Building the Prompt

Augmentation is the step where you assemble the final prompt: query + retrieved chunks + system instructions. Easy to underrate, easy to get wrong.

The Anatomy of a Good RAG Prompt

SYSTEM: You are a compliance assistant for HDFC Bank's branch staff. Answer questions using ONLY the context provided below. If the answer isn't in the context, say "I don't have that information in my knowledge base — please refer to the policy team." Always cite the source document and section number at the end. CONTEXT: [Source: RBI Master Direction LRS 2024-25, Section 3.1.2] Under the Liberalised Remittance Scheme, resident individuals may remit up to USD 250,000 per financial year for any permissible current or capital account transaction... [Source: HDFC Internal Policy LRS-OPS-2024, Section 4.2] Branch staff must verify customer PAN and obtain Form A2 before processing any LRS remittance above USD 25,000... [Source: ...3 more retrieved chunks ...] QUESTION: What is the LRS limit for resident individuals in FY 2025-26, and what documents does the branch need to collect? ANSWER:

The Levers You Can Pull

Element Why It Matters
System prompt with explicit grounding instruction "Use ONLY the context" reduces hallucination materially
"Don't know" escape hatch Tells the model it's okay to say "I don't have that" — instead of inventing
Citation requirement in instructions Forces the LLM to ground claims to specific chunks — auditable
Chunk separation with source markers "[Source: doc-X-section-Y]" before each chunk → LLM can cite cleanly
Order of chunks Put most-relevant chunks at the START and END (recall lost-in-the-middle from Deck 1)
Query at the end Right before the model generates → max attention

Common mistake: dumping retrieved chunks with no source markers, no system instruction, no "don't know" escape. The model then improvises confidently and you get hallucinations attributed to chunks that don't actually support the claim.

🧠Step 8: Generation — The Final Mile

What Happens in This Step

The constructed prompt goes to the LLM. The LLM produces an answer grounded in the retrieved context, ideally with citations. Sounds simple — there are still real choices to make.

The Choices That Actually Move the Needle

Choice Trade-Off
Which LLM Frontier (Claude 4.6, GPT-4.5, Gemini 3) for hard reasoning; cheaper models (Haiku, GPT-4o-mini, Gemini Flash) for high-volume simple Q&A. Don't default to the biggest model — measure first.
Temperature For factual RAG: temperature 0-0.3. Higher temperatures invite more "creative" deviations from the retrieved context.
Streaming output Stream tokens to the user — perceived latency drops 5-10×. Even if total time is the same.
Structured output For programmatic use, force JSON / Pydantic schema. Modern LLMs support this natively (OpenAI, Anthropic, Gemini).
Citation rendering Decide format: inline ([1], [2]) or footnote-style. Decide whether to link back to the source.
Refusal handling When context doesn't support an answer, the LLM should refuse — verify your prompt elicits this reliably

Post-Processing the Answer

  • Citation validation — does each citation point to a real chunk in the retrieved context? If not, drop it.
  • Toxicity / PII / compliance filters — especially for customer-facing answers
  • Confidence scoring — use the LLM's own logits or a separate "rate this answer's confidence" pass to surface low-confidence answers for human review
  • Caching — if the same query + same retrieved chunks → cache the answer. Saves cost on FAQ-style traffic.

Generation rarely fails on its own. If your final answer is bad, the cause is almost always upstream: bad chunking, bad retrieval, or a bad prompt. Switching LLMs is the last thing to try, not the first.

🛠️Part 3

RAG Frameworks — LangChain, LlamaIndex, Haystack, DSPy

⚖️Build From Scratch, or Use a Framework?

The first decision: do you wire up the 8 steps yourself, or stand on a framework?

🛠️ Build From Scratch

Pros:

  • Full control over every line
  • No framework upgrade headaches
  • Easier to debug and reason about
  • Often less code for narrow use cases

Cons:

  • You build all the plumbing (loaders, splitters, retrievers, tracing)
  • Re-inventing tested patterns
  • Slow to evolve (e.g., add a new VDB integration)

Best for: production systems where you've already prototyped and now want minimal dependencies and maximum clarity.

📦 Use a Framework

Pros:

  • Hundreds of pre-built integrations (loaders, embedders, VDBs)
  • Battle-tested patterns; community examples
  • Built-in tracing, observability hooks
  • Faster iteration from idea to working prototype

Cons:

  • Abstractions hide what's happening
  • Breaking changes across versions (LangChain 0.1 → 0.2 → 0.3 → 1.0)
  • 30-40% more code than minimal Python for trivial cases
  • Performance overhead (10-50ms per call vs minimal)

Best for: prototypes, MVPs, and most production systems too — the productivity gain usually justifies the overhead.

The pragmatic answer for 2026: Start with a framework. Once you understand exactly what the framework is doing for you, you can decide whether to keep it, replace specific pieces, or migrate to from-scratch code. Don't over-engineer the foundation.

RAG Evaluation — Measuring What Matters

🎯Why Evaluation Is the Difference Between "Demo" and "Production"

RAG systems are easy to prototype, hard to keep working. The team that ships a flashy demo and the team that runs reliable production look very different from the inside. The difference is evaluation.

The Failure Modes Eval Catches

Without Eval With Eval
"It looked good when I tested it" Quantitative scores across 100+ representative queries
Silent quality drift after every prompt tweak Regression tests on every PR — drops in faithfulness block merge
"User complained, no idea why" Failed query → drop into eval pipeline → root-cause in minutes
Can't compare retrieval strategies fairly A/B test naive vs reranked vs HyDE on same eval set; pick the winner
"Should we switch to GPT-5?" Run eval on both; the numbers tell you
Compliance can't sign off — no evidence of quality "Faithfulness ≥0.85 on 500 golden queries, evaluated monthly"

The Two-Layer Failure Model

Every RAG failure happens at one of two layers:

  • Retrieval failure — the right content didn't reach the prompt. Even a perfect LLM can't answer correctly without the right context.
  • Generation failure — the right content reached the prompt, but the LLM didn't use it correctly (hallucination, irrelevant detour, refusal when shouldn't).

Treating these as separate evaluation layers is the foundation of structured RAG quality work — and what RAGAS, DeepEval, and TruLens all do.

The 2026 reality: shipping RAG to production without an eval loop is malpractice. You will not catch regressions. Your users will. Your auditors will. Build the eval loop on day 1, not when something breaks.

🔍Retrieval Metrics — Did We Get the Right Chunks?

You evaluate retrieval against a ground-truth set: for each query, you've labeled which chunks (or documents) are "truly relevant". Then you compute these five metrics on what the retriever actually returned.

Metric Formula What It Measures Banking Example Interpretation
Precision@k (# relevant in top-k) ÷ k Of what the retriever returned, what fraction was actually useful? Of 5 retrieved policy chunks, how many were really about the user's question?
Recall@k (# relevant in top-k) ÷ (total relevant) Of all the useful chunks, what fraction did we manage to retrieve? Did we find every section of the policy that answers the question?
Hit Rate (Hits@k) 1 if ANY relevant chunk in top-k, else 0 Did we get at least ONE useful chunk? Binary signal. Will the LLM at least see something relevant for this query?
MRR (Mean Reciprocal Rank) 1 ÷ (rank of FIRST relevant chunk) How early in the list did the FIRST relevant chunk appear? Did the right policy section appear at position #1 or #18?
NDCG@k Discounted gain, normalized Are the most relevant chunks ranked at the TOP? Position-weighted. The richest holistic signal — captures both "did we find it" and "where in the list"

How They Interact

  • Precision focuses on noise: high precision = few junk chunks. Critical for keeping context tight.
  • Recall focuses on completeness: high recall = nothing important got missed. Critical for multi-part questions.
  • MRR and NDCG focus on ranking: even if you found the relevant chunk, is it at the top? (Matters because of lost-in-the-middle — see Deck 1.)
  • Hit Rate is the absolute floor: if hit rate is low, nothing else matters — you didn't find anything useful at all.

What "k" to use? Match the k to how many chunks you pass to the LLM. If you pass top-5 to the prompt, evaluate Precision@5, Recall@5, NDCG@5. Don't evaluate at k=20 if you only use top-5 — the metric won't reflect production behavior.

📝Generation Metrics — Did the LLM Use the Chunks Properly?

Even with perfect retrieval, the LLM might still hallucinate, ignore the context, or wander off-topic. Generation metrics catch this.

Metric What It Measures What a Bad Score Means
Faithfulness Every factual claim in the answer must be supported by the retrieved context. No hallucination. The LLM is inventing things not in the context. Hallucination risk.
Answer Relevancy Does the answer actually address the user's question? The LLM is rambling, evasive, or answering a different question than asked.
Context Precision Of the retrieved chunks, what fraction were actually used / relevant? You're stuffing too much irrelevant context — distractor risk; wasting tokens.
Context Recall Did the retrieved context contain everything needed to fully answer? Retrieval missed information the LLM needed → incomplete answers.
Answer Correctness Does the answer match the ground-truth answer? (Requires reference answers.) Even if grounded, the answer is wrong — bigger problem upstream.
Context Utilization How much of the relevant context did the answer actually use? The LLM ignored useful chunks — possibly cut content or got distracted.

How These Get Measured (LLM-as-a-Judge)

The trick: for most of these, there's no ground-truth scoring rubric a regex can apply. So eval frameworks use an LLM as a judge:

  • For faithfulness: break the answer into atomic claims, then ask "is this claim supported by the context? Yes/No" for each.
  • For answer relevancy: ask the LLM to generate questions that the answer is actually answering, then compare to the original question.
  • For context precision: rank each retrieved chunk by how much it contributed to the answer; weight by position.

This is called the LLM-as-a-judge pattern — and it's how RAGAS, DeepEval, and TruLens all work.

Caveat on LLM-as-judge: the judge LLM has its own biases. Use a strong model (Claude 4.6 Opus, GPT-4.5) as judge, not a cheap one. And spot-check the judge's labels against human labels periodically to keep it honest.

🚫Why BLEU, ROUGE, BERTScore Are Wrong for RAG

If you're coming from machine translation or summarization research, you might reach for BLEU, ROUGE, METEOR, or BERTScore. These don't work for RAG — and using them gives misleading scores. Here's why.

What They Actually Measure

Metric Origin What It Measures
BLEU Machine Translation (2002) n-gram overlap between candidate & reference text
ROUGE Summarization (2004) Recall-based n-gram overlap
METEOR Machine Translation Word matches with stemming + synonyms
BERTScore NLP eval generally (2020) Embedding-based similarity between candidate & reference

Why They Mislead in RAG

All of these measure surface similarity to a reference text. None of them measure:

  • Whether the answer is factually grounded in the retrieved context — a fluent-sounding hallucination scores HIGH on BLEU/ROUGE if its wording happens to overlap with the reference
  • Whether the answer correctly used the retrieved chunks
  • Whether retrieval found the right material in the first place

A RAG system that completely ignores its retrieved context can still score well on ROUGE if the LLM's training-data memory happens to overlap with the reference answer. This means ROUGE can give you false confidence.

What to Use Instead

For RAG specifically, use retrieval-aware metrics that measure the actual failure modes:

  • Faithfulness — is the answer supported by retrieved context?
  • Answer Relevancy — does it address the question?
  • Context Precision & Recall — was retrieval good?
  • Answer Correctness (if you have ground truth) — is it right?

These are exactly what RAGAS, DeepEval, and TruLens give you out of the box. Use them.

The "BLEU/ROUGE inadequacy for RAG" argument is well-documented in 2024-26 RAG eval literature (RAGAS paper, DeepEval docs, TruLens whitepapers). Traditional metrics weren't designed for retrieval-augmented systems.

⚖️The LLM-as-a-Judge Pattern: How & Why

Every modern RAG eval framework uses an LLM as the scoring engine. Understanding why — and the pitfalls — protects you from over-trusting these scores.

The Basic Pattern

For each metric, the framework gives the judge LLM a prompt like:

SYSTEM: You are evaluating a RAG answer for faithfulness. A claim is "faithful" only if it is directly supported by the provided context. Score each claim independently. QUESTION: {original user question} CONTEXT: {retrieved chunks} ANSWER: {RAG-generated answer} TASK: 1. Break the answer into atomic factual claims. 2. For each claim, mark "YES" if supported by context, else "NO". 3. Output: faithfulness = (# YES) / (# total claims)

Run this for many examples, average → you have your eval metric.

Why This Works

  • Strong frontier LLMs are surprisingly good judges — they correlate well with human labels on most tasks
  • Cheap — judge costs are $0.001-0.003 per test case; 200-question eval costs ~$1
  • Scalable — run nightly on 1000s of examples
  • Reference-free — for many metrics, doesn't need pre-written "gold" answers

The Pitfalls You Need to Know

  • Judge LLM bias. Models tend to favor verbose answers, certain styles, and outputs from their own family. Use a different model family as judge than as generator when possible.
  • Position bias. If comparing two answers, the judge can favor whichever came first in the prompt. Always shuffle order.
  • Lock the judge model. If you change judge from GPT-4o to Claude 4.6, your scores will shift. Lock it in and only change deliberately.
  • Spot-check with human labels. Periodically (every 1-3 months), label 50-100 examples by hand and compare to the judge's scores. If they diverge by >10%, recalibrate your judge prompt.
  • Use a strong judge. Cheap models give noisy scores. Use Claude 4.6 Opus, GPT-4.5, or Gemini 3 Pro for judging — even if the system being judged uses cheaper models.

The honest framing: LLM-as-judge gives you directional signals — "this version is better than that version" — much more reliably than absolute scores. Use it for relative comparisons; don't read absolute values to 3 decimal places.

🔀Technique 1: Hybrid Retrieval (BM25 + Vector + RRF)

Covered in depth in Part 2 — the foundation technique that should be in every production RAG by default. Quick recap of when and why.

The Recipe

  1. Run BM25 (keyword) retrieval in parallel with vector retrieval — each returns top-50
  2. Combine the rankings using Reciprocal Rank Fusion (RRF): score(d) = Σᵢ 1 / (k + rank_i(d)), where k = 60
  3. Take the top-100 fused candidates and pass to the next stage (filtering / reranking)

Why It Beats Pure Semantic

BM25 Wins When Vector Wins When
Exact-match terms: account numbers, PAN, IFSC, ticker symbols, section refs Paraphrases: "credit denied" ↔ "loan rejected"
Rare technical jargon the embedding model wasn't well-trained on Synonyms: "interest rate" ↔ "yield" ↔ "coupon"
Out-of-distribution domain terms Cross-language search
Misspelled keywords (with stemming) Semantic relationships embedding learned

Empirical headline: contextual hybrid retrieval reduces top-20 retrieval failure rate by 49% compared to pure vector — even before applying a reranker. The numbers come from Anthropic's Contextual Retrieval study (next slide).

When to skip it: rarely. The only case is if your queries are guaranteed to be natural-language paraphrases with no exact terms (e.g., user feedback sentiment analysis). For 99% of BFSI RAG, hybrid wins.

🎖️Technique 2: Reranking with Cross-Encoders

The single highest-leverage technique you can add after hybrid retrieval. Often the biggest jump in quality, for the smallest amount of code.

The Key Distinction: Bi-Encoder vs Cross-Encoder

Bi-Encoder (what embeddings are) Cross-Encoder (what rerankers are)
How it scores Embed query and doc separately → cosine similarity Concatenate (query + doc) → pass through transformer → scalar score
Speed ⚡ Fast — millions of docs in milliseconds (pre-computed vectors) 🐢 Slow — must score each (query, doc) pair fresh
Accuracy Decent — limited by how well embeddings capture relevance ⭐ Much higher — true cross-attention between query & doc
When to use First-stage retrieval over millions of docs Re-scoring the top-50 to 100 from first-stage

The Production Pattern

  1. Hybrid retrieval brings you to top-100 candidates (fast)
  2. A cross-encoder reranker scores each (query, candidate) pair (slower, but only 100 calls)
  3. Take top-5 to top-10 reranked → pass to LLM

Why this is fast enough for production: 100 cross-encoder calls completes in ~50-200ms with modern rerankers — within latency budget.

🪄Technique 3: Contextual Retrieval (Anthropic)

Anthropic's September 2024 contribution to the RAG playbook. One of the simplest advanced techniques to understand — and one of the most effective. The intuition: chunks lose context when separated from their parent document, so add the context back before embedding.

The Problem It Solves

Imagine a chunk: "The company's revenue grew 3% over the previous quarter."

Which company? Which quarter? On its own, the chunk is useless. Embedding it as-is means the chunk will match queries about any company's quarterly growth — drowning the signal you actually want.

The Fix: Pre-Pend LLM-Generated Context

Before embedding each chunk, ask an LLM to read the chunk together with its parent document and generate a short context paragraph. Embed the chunk + context, not just the chunk.

The Reported Impact (Anthropic, Sept 2024)

  • Contextual embeddings alone: 35% reduction in top-20 retrieval failures
  • + Contextual BM25: 49% reduction
  • + Cross-encoder reranker: 67% reduction

These are stacked — adding all three is the recipe Anthropic recommends.

Cost concern? Generating context for every chunk sounds expensive — but with prompt caching (the document is cached, only the chunk changes per call), Anthropic reports the indexing cost is ~$1.02 per million tokens of documents. Affordable.

Source: Anthropic, "Introducing Contextual Retrieval" (September 19, 2024). Numbers from Anthropic's own production benchmarks. The technique works with any LLM; Anthropic suggests Claude Haiku as the contextualizer for cost.

🎭Technique 4: HyDE (Hypothetical Document Embeddings)

The clever trick: queries and documents aren't shaped the same way. Queries are short and often vague; documents are long and detailed. Embedding similarity between them is structurally weak. HyDE bridges that gap.

The Idea

Instead of embedding the user's query directly, first:

  1. Ask an LLM to generate a hypothetical answer to the query — what a good document on this topic might say
  2. Embed that hypothetical answer
  3. Use it to search the vector DB

The hypothetical answer is in the same "shape" as the documents — so the embedding similarity is structurally better, even if the hypothesized answer is factually wrong.

When HyDE Helps Most

  • Short / vague queries — "explain X", "how does Y work" — vector search underperforms; hypothetical fills in context
  • Domain-mismatch — user uses casual language ("when do I get my money back?"), docs use formal ("redemption timelines for liquid mutual funds")
  • When you can't fine-tune embeddings on domain pairs — HyDE is a no-fine-tuning alternative

Cost & latency: Adds one LLM call per query (the hypothesizer). For low-volume / high-value queries → worth it. For high-volume customer chat → use a cheap model (Haiku, GPT-4o-mini) or skip it. Often contextual retrieval gives similar gains at lower per-query cost.

Source: Gao et al., "Precise Zero-Shot Dense Retrieval without Relevance Labels" (HyDE paper, 2022). Well-replicated; supported by every major framework (LangChain, LlamaIndex) out of the box.

🌀Technique 5: Multi-Query / RAG Fusion

The intuition: users phrase questions one way, but the same idea could be asked many ways. Generate multiple phrasings, retrieve for each, fuse the results.

How It Works

  1. Take the user's query: "How do I report an unauthorized transaction?"
  2. Ask an LLM to generate 3-5 alternative phrasings:
    • "What's the procedure for disputing a charge I didn't make?"
    • "Steps to report fraud on my account"
    • "How to file a complaint about suspicious transactions"
    • "RBI guidelines on customer liability for unauthorized transactions"
  3. Run retrieval for each phrasing in parallel → 5 ranked lists of chunks
  4. Combine the 5 lists using Reciprocal Rank Fusion (RRF) — same algorithm as hybrid search
  5. Pass the top fused chunks to the LLM

Why It Helps

  • Catches different relevant chunks — different phrasings retrieve different (but valid) docs. Union is broader than any one.
  • RRF gives bonus weight to chunks multiple queries agreed on — built-in confidence signal
  • Handles ambiguous queries gracefully — if the query could mean two things, you cover both interpretations
  • Easy to implement — most frameworks have it built-in (LangChain MultiQueryRetriever, LlamaIndex sub-question)

RAG Fusion: The Generalized Variant

RAG Fusion generalizes Multi-Query: any set of related queries can be fused — not just LLM-rephrasings. For example:

Source of Query Variants Example
LLM rephrasing (vanilla Multi-Query) "Margin call" → 5 alternative phrasings
Query decomposition (next slide) "Which subsidiaries..." → "List Adani subsidiaries" + "Which have loans > 100Cr?"
Step-back questions "What was inflation in May?" → "What is inflation?" (broader context)
HyDE hypotheticals (combinable) Use HyDE-generated text as one of the fusion inputs

Cost trade-off: 5× more retrieval calls. For low-cost local retrieval, fine. For paid VDB calls + paid LLM rephrasing, multiplies latency & cost. Use when retrieval quality is the bottleneck — not as a default.

🧩Technique 6: Query Decomposition (Multi-Hop)

The trick for queries that bundle multiple questions. Break complex queries into atomic sub-questions, retrieve for each, combine answers.

When It's Needed

A single query that looks like one question but is actually 2-3:

  • "What was HDFC's Q3 profit and how does it compare to ICICI's Q3?" → two retrieval needs
  • "Which RBI circulars affect digital lending and what are the compliance deadlines?" → list + dates
  • "Which subsidiaries of Adani have outstanding loans > ₹100Cr from PSU banks?" → multi-hop graph traversal disguised as a single question

Naive RAG retrieves chunks similar to the full query — usually finds chunks about ONE of the sub-questions, misses the others.

How Query Decomposition Works

  1. LLM analyzes the query and decomposes it into atomic sub-questions:
    Original: "What was HDFC's Q3 profit and how does it compare to ICICI's?" Sub-Q 1: "What was HDFC Bank's Q3 FY24-25 profit?" Sub-Q 2: "What was ICICI Bank's Q3 FY24-25 profit?" Synthesis: "Compare the two numbers."
  2. Retrieve and answer each sub-question independently
  3. Synthesize a final answer using the LLM, given all sub-answers

Production Patterns

Variant How It Works Best For
LlamaIndex Sub-Question Query Engine Built-in; decomposes, fans out, synthesizes Drop-in for general multi-hop queries
ReAct-style step-by-step Agent decomposes one step at a time, deciding as it goes Open-ended multi-step reasoning; uses LangGraph well
Plan-and-execute Agent first writes the plan, then executes each step Predictable agent flows; auditable plans

Trade-off: Each sub-question is another LLM + retrieval round-trip. Latency & cost can be 3-5× a single retrieve. Use when the query genuinely needs it — skip for simple lookups.

✂️Technique 7: Advanced Chunking Strategies

Covered in Part 2 — restating here because chunking is so important it sits in the "advanced techniques" toolbox too. These are the chunking strategies that materially move quality.

Strategy Mechanism BFSI Use Case
Semantic chunking Embed sentences; split at semantic shifts (when adjacent similarity drops below threshold) Multi-topic analyst reports, long research notes
Sentence-window retrieval Embed individual sentences for precision; expand to ± N sentences in the prompt for context Dense regulatory text where you need precision AND context
Parent-child chunking Embed small "child" chunks; return larger "parent" chunks to the LLM Hierarchical docs (policies with sections; contracts with clauses)
Auto-merging retrieval If multiple sibling chunks of the same parent are retrieved, return the parent instead Long policy docs where adjacent sections often need to be read together
Late chunking (Jina, 2024) Embed the whole long doc first, THEN chunk the token-level embeddings — each chunk's embedding reflects full-doc context When you need each chunk to "know" what document it came from semantically
Agentic chunking An LLM reads the doc and decides where chunks should start/end based on meaning High-stakes / low-volume content (board minutes, regulatory filings)

The "Right" Chunking Strategy For Your Use Case

  • Mixed document types, varied topics → Semantic chunking
  • Strict hierarchy (policy → section → clause) → Parent-child + auto-merge
  • Dense regulatory text where every sentence matters → Sentence-window
  • Q&A pairs / FAQs → One Q&A = one chunk; no splitting needed
  • Heterogeneous corpus where one strategy doesn't fit → Per-document-type chunking (different strategy per source)

Recall from Part 2: optimized semantic chunking achieves 0.79-0.82 faithfulness vs 0.47-0.51 for naive fixed-size — roughly 70% relative improvement. The single biggest quality lever after retrieval pipeline.

🌲Technique 8: RAPTOR (Recursive Abstractive Tree Indexing)

What if your knowledge base has different "altitudes" of information — detailed sentences AND high-level themes? RAPTOR builds a tree of progressively summarized clusters, so you can retrieve at the right level of abstraction.

The Build Process

  1. Chunk and embed at leaf level (regular chunks)
  2. Cluster the leaf embeddings — group semantically similar chunks
  3. Summarize each cluster with an LLM → a new, higher-level node
  4. Embed the summaries
  5. Recurse: cluster the summaries, summarize the clusters, embed those summaries…
  6. Continue until you have a single root summary

The result: a tree where leaves are detail and the root is the overarching theme.

Retrieval at Query Time

At query time, embed the query and retrieve from all levels of the tree. For:

  • Specific factual questions ("What's the exact interest rate?") → match leaf chunks
  • Broad thematic questions ("What are the major risks discussed in this report?") → match high-level summaries
  • Mixed questions → retrieval naturally returns a mix of levels

When To Reach For RAPTOR

Good Fit Poor Fit
Corpus is large, conceptually hierarchical (research reports, books, long manuals) Q&A-style or short-document corpora
Users ask both fine and broad questions Users only ask narrow lookup questions
Knowledge base is relatively static (rebuild cost worth it) Documents change daily (tree rebuild becomes expensive)

The cost trade-off: RAPTOR's tree building consumes a lot of LLM tokens (cluster summaries × multiple levels). For a 100K-chunk corpus, that's tens of thousands of LLM calls at index time. Like GraphRAG (slide 54), better for static knowledge bases.

Source: Sarthi et al., "RAPTOR: Recursive Abstractive Processing for Tree-Organized Retrieval" (Stanford, 2024). Reported ~20% improvement on QuALITY narrative-comprehension benchmark over flat chunking. Supported in LlamaIndex.

🪞Technique 9: Self-RAG (Self-Reflective Retrieval)

The pattern: let the LLM decide when retrieval is needed, what to retrieve, and whether the retrieved chunks are actually useful — using reflection tokens.

The Three Reflection Steps

  1. "Do I need to retrieve?" — for some queries (like "summarize what we discussed earlier"), retrieval is unhelpful. The model can skip it.
  2. "Are these retrieved chunks actually relevant?" — after retrieval, the model assesses each chunk. Discards weak ones before answering.
  3. "Did my answer use the retrieved chunks faithfully?" — after generating, the model self-critiques. If the answer drifted from context, it can regenerate.

Each step uses special reflection tokens (e.g., [Retrieve?], [IsRel], [IsSup]) the model is fine-tuned to produce.

Why It Helps

  • Avoids unnecessary retrieval — saves cost & latency on queries that don't need it
  • Filters out irrelevant chunks at the source — before they pollute the prompt
  • Built-in faithfulness check — catches hallucination before it reaches the user
  • Better calibrated uncertainty — can say "I don't have enough info" more reliably

The Catch

Vanilla Self-RAG requires fine-tuning the LLM on reflection tokens — most teams won't do that. But the idea is portable: you can implement "Self-RAG-style" reasoning with multiple prompt passes using any LLM:

  • Pass 1: "Given this query, do we need retrieval? Yes/No"
  • Pass 2 (if needed): retrieve, then "For each of these chunks, is it relevant? Yes/No"
  • Pass 3: generate answer using only the kept chunks
  • Pass 4: "Is this answer fully supported by the chunks? Yes/No. If no, revise."

This loses some efficiency but works with any LLM. Trade-off: more LLM calls per query.

Source: Asai et al., "Self-RAG: Learning to Retrieve, Generate, and Critique through Self-Reflection" (ICLR 2024). Original paper requires fine-tuning; production-friendly variants approximate the behavior with prompting.

🔧Technique 10: CRAG (Corrective RAG)

The idea: What if retrieval returns weak or irrelevant chunks? Instead of feeding them to the LLM anyway, detect the failure and take corrective action — often by falling back to web search.

How CRAG Works

  1. Retrieve normally from your vector DB
  2. Score retrieved chunks for relevance using a lightweight evaluator (small LLM or fine-tuned classifier)
  3. Bucket the result:
    • Correct (relevance high) → use as-is
    • Incorrect (relevance low) → discard internal retrieval; fall back to web search (Tavily, Brave, Google Search API)
    • Ambiguous (mixed) → use a combination: retrieved + web search results
  4. Generate with whatever survived the corrective step

Why It's Powerful

  • Handles "knowledge gap" gracefully — if your KB doesn't have the answer, web does
  • Reduces "confident wrong answers" — the corrective step catches the failure mode where retrieval pulls similar-but-wrong content
  • Combines internal + external knowledge — great for queries that span "our policies" and "current market news"

BFSI Caveat: Web Search Fallback Has Risks

  • Web sources are not vetted — quality varies wildly
  • Banking compliance officers may forbid external data in customer-facing answers
  • The web fallback should be labeled clearly in the response ("from external source X")
  • Consider restricting web fallback to a whitelist of trusted sources (RBI website, SEBI portal, IRDAI, official news) rather than open web

BFSI-appropriate variant: Replace the "web search" fallback with "search a broader internal knowledge base" or "escalate to human expert". Same correction pattern, no external-data risk.

Source: Yan et al., "Corrective Retrieval Augmented Generation" (2024). Production implementations in LangGraph and LlamaIndex. The pattern works with or without web fallback — the relevance-scoring + branching is the core idea.

🚦Technique 11: Adaptive RAG (The Query Router)

The idea: Different queries deserve different retrieval strategies. A query classifier (small LLM or trained model) routes each query to the right pipeline.

The Routing Logic

At query time, a router decides the path:

Query Type Route To
"Hi" / "Thanks" / "How are you?" No retrieval — direct LLM response
"What's 2 + 2?" / "Calculate 7% interest on ₹5L over 3 years" Calculator tool, not retrieval
"What's NIFTY trading at right now?" Live API call (NSE, Bloomberg), not RAG
Simple lookup: "What's the LRS limit?" Naive RAG — single retrieve, single generate
Multi-hop: "Which subsidiaries have loans over X?" Query decomposition + multi-retrieval
Vague / short query HyDE — generate hypothetical then retrieve
Network / relationship query GraphRAG (next slide)

Why It Matters in Production

  • Saves cost — don't run an expensive multi-hop pipeline for "what's the LRS limit"
  • Saves latency — simple queries get simple answers fast
  • Improves quality — complex queries get the technique they actually need
  • Mirrors how humans work — you mentally classify queries before tackling them

Production Implementation

  • The router itself is a small LLM call with a classification prompt — ~10-50ms, very cheap
  • Fine-tune the router over time using production logs — improves accuracy
  • LangGraph's conditional edges are purpose-built for this pattern
  • Default to a safe path (full pipeline) when the router is unsure

Adaptive RAG pattern from Jeong et al., "Adaptive-RAG: Learning to Adapt Retrieval-Augmented Large Language Models through Question Complexity" (2024). LangGraph's branching makes this trivially implementable in 2026.

🕸️Technique 12: GraphRAG

Introduced in Deck 1 as a teaser — now the full picture. When relationships matter more than similarity, GraphRAG outperforms vector RAG. Microsoft's open-source GraphRAG has 31.6K+ GitHub stars in 2026.

The Build Process

The Three Query Modes

  • Local Search — entity-centric questions; uses the immediate neighborhood of identified entities. Best for "What's X's relationship to Y?".
  • Global Search — thematic / summarizing questions; aggregates pre-computed community summaries. Best for "What are the major themes in this corpus?".
  • DRIFT Search — hybrid; starts at the global level, drills down to specifics. Best for "Which-of-X meet condition Y?".

The cost trade-off (recap from Deck 1): GraphRAG indexing is expensive — Microsoft reports millions of LLM tokens for a 100K-chunk corpus. Best for static or slow-changing knowledge bases (regulations, master directions, technical manuals). Not for live transaction data.

Source: Microsoft Research GraphRAG (April 2024 launch, 31.6K+ stars as of 2026). Uses Leiden algorithm for community detection (Traag et al. 2019). Local/Global/DRIFT search modes per Microsoft GraphRAG docs.

🤖Technique 13 (Bonus): Agentic RAG

The umbrella concept — wrap RAG inside an agent that plans, decides, retrieves, validates, and iterates. Instead of "retrieve once and answer", the agent orchestrates retrieval as part of multi-step reasoning.

What an Agentic RAG Loop Looks Like

  1. Plan: "To answer this, I need to: (a) find subsidiaries of Adani, (b) for each, check loan outstanding"
  2. Retrieve (round 1): "List subsidiaries of Adani Group"
  3. Reason: "I found 8 subsidiaries. Now for each…"
  4. Retrieve (round 2-9): One retrieval per subsidiary
  5. Aggregate & validate: "Do my retrieved facts sum to a coherent answer?"
  6. Self-critique: "Are there gaps? Should I retrieve more?"
  7. Generate final answer with citations

The Building Blocks (Most Already Covered)

  • Query decomposition (Technique 6) for planning
  • Adaptive routing (Technique 11) for picking sub-strategies
  • Self-RAG patterns (Technique 9) for self-critique
  • CRAG (Technique 10) for corrective action
  • Tools beyond RAG — calculator, SQL, web search, internal APIs
  • State management & orchestration — LangGraph, LlamaIndex Workflows

BFSI Use Cases Where Agentic RAG Shines

Use Case Why Agentic?
Credit underwriting copilot Multi-step: pull customer history → check exposure → look up similar past cases → produce recommendation
AML investigation copilot Investigate-as-you-go: each fact uncovered triggers the next retrieval
Audit assistant Cross-reference current findings against historical reports, regulatory observations
Wealth advisory Combine portfolio data, market data, regulatory limits, customer profile

The agentic trade-off: Far more flexible and powerful than naive RAG — but also more expensive (multiple LLM + retrieval rounds), slower (sequential reasoning), and harder to evaluate & debug. Start with the simplest pattern that works; reach for agentic RAG when simpler patterns hit a ceiling.

🎯Choosing Advanced Techniques: A Decision Table

If your problem is... Reach for...
Naive vector retrieval misses exact-match queries Hybrid retrieval (BM25 + Vector + RRF) — Technique 1. The default.
Recall is OK but top-5 has too much junk Reranking with cross-encoder — Technique 2. Biggest single quality jump for least code.
Chunks lose meaning out of context (e.g., "growth was 3% last quarter") Contextual Retrieval — Technique 3. Anthropic's 35-67% improvement recipe.
Short / vague queries underperform HyDE — Technique 4. Bridge the query↔doc embedding gap.
Same idea phrased many ways; some phrasings work, some don't Multi-Query / RAG Fusion — Technique 5.
Multi-part questions ("X AND Y compared to Z") Query Decomposition — Technique 6.
Chunking strategy is the bottleneck Advanced chunking (semantic, parent-child, sentence-window) — Technique 7.
Mix of detail-level and theme-level questions RAPTOR — Technique 8 (multi-level summaries).
Many irrelevant chunks polluting prompts Self-RAG-style filtering — Technique 9. Score each chunk's relevance before using.
KB sometimes doesn't have the answer; need fallback CRAG (Corrective RAG) — Technique 10.
Mix of simple lookups + complex multi-hop queries Adaptive RAG (query router) — Technique 11.
Questions about entity relationships, networks, themes across docs GraphRAG — Technique 12. (Expensive to index; works best on static KBs.)
Open-ended multi-step investigation tasks Agentic RAG — Technique 13. Wraps the others in an orchestration loop.

The Order I'd Add These In

  1. Start: Hybrid retrieval + Reranker (techniques 1 + 2). 80% of teams stop here and ship.
  2. If quality still gaps: Contextual Retrieval (technique 3) or improved chunking (technique 7)
  3. If specific query types fail: add the matching technique (HyDE / decomposition / multi-query)
  4. If query mix is varied: Adaptive RAG router (technique 11)
  5. For specialized cases: RAPTOR, GraphRAG, agentic patterns — only when there's a clear reason

Add complexity reluctantly. Each technique adds latency, cost, and surface area for bugs.

Production & Wrap-Up

✅RAG in Production: Best Practices

🏗️ Architecture & Design

  • Separate ingestion from serving — different SLAs, different scaling profiles, different failure modes. Don't try to do both in one process.
  • Make embedding model swappable — config-driven, not hard-coded. When you upgrade, you should be able to re-index without touching application code.
  • Build hybrid retrieval from day 1 — adding BM25 later is harder than starting with it.
  • Add a reranker as the first "advanced technique" — biggest quality win per line of code.
  • Plan for re-indexing — model upgrade, chunk strategy change, schema change. It WILL happen. Make it routine, not heroic.

📊 Observability & Evaluation

  • Trace every step — query → retrieved chunks → final prompt → answer. LangSmith, TruLens, OpenTelemetry — pick one and use it.
  • Maintain a golden eval set — 50-500 real queries with expected answers / relevant docs. Run nightly.
  • Alert on quality drops — faithfulness drops > 5% → page someone. Same as you'd page for an outage.
  • Capture user feedback — thumbs-up / down on answers feeds back into eval set and retrieval tuning.
  • Log retrieved chunks per query — when something goes wrong, you need to know what the retriever returned.

🔒 Security & Compliance (BFSI Critical)

  • Multi-tenant isolation — vector DB namespaces / collections per business unit; no leakage across tenants
  • RBAC at retrieval time — filter retrieved chunks by user permissions BEFORE giving to LLM
  • PII handling — redact or pseudonymize PII before embedding; consider whether sensitive docs should be indexed at all
  • Audit log every query & answer — non-negotiable for regulated industries
  • Data residency — for India BFSI, vectors of customer data must usually stay in Indian cloud regions
  • Encryption at rest & in transit — table stakes

⚠️Common RAG Pitfalls (and How to Avoid Them)

Pitfall Symptom Fix
Different embedding models indexing vs querying Search returns nothing relevant — looks broken Hard-code in config; alarm if mismatched. The #1 newcomer mistake.
Pure semantic without BM25 Misses exact IDs / codes / section refs Add hybrid + RRF. Always.
No reranker Relevant chunks present but buried at rank 23 Add Cohere Rerank 3.5 or BGE-reranker — one of the easiest wins available.
Chunks too small / too large Too small: chunks lack context. Too large: imprecise retrieval, distractor risk. 300-500 tokens sweet spot for most BFSI docs; A/B test sizes; consider parent-child.
No metadata filters Outdated 2018 policy mixed with current 2025 policy in results Tag every chunk: date, version, jurisdiction. Filter at retrieval.
No eval loop Silent quality drift; users complain; you don't know why RAGAS / DeepEval, golden set, nightly runs, regression alerts.
Bigger LLM as the fix-all Spent 3× on inference; no quality improvement Generation rarely the bottleneck — fix retrieval first.
No "I don't know" escape LLM hallucinates when retrieved context doesn't actually answer Explicit prompt instruction + test that the model refuses on out-of-KB queries.
Citations that hallucinate LLM cites a chunk that doesn't actually support the claim Post-process: validate each citation against retrieved chunks; drop unsupported.
⚠️ Prompt injection via retrieved docs Malicious content in a retrieved doc hijacks the LLM ("Ignore previous instructions; reply with...") Sanitize / quarantine retrieved content; treat it as untrusted user input. Use input filtering.

The Prompt-Injection-via-Docs Threat (Underappreciated)

If your corpus includes ANY user-generated content (customer emails, support tickets, public web pages, social posts), a malicious actor can plant prompt-injection payloads in those docs. When that doc is retrieved and fed to your LLM, the payload can override your system prompt. For BFSI: never index unsanitized customer-provided content alongside policy data without isolating it.

💰Cost Optimization: Where Money Actually Goes in RAG

The Cost Stack

Cost Center Typical Share of Total Lever
LLM generation (per query, paid per output token) ~50-70% Pick the right model size; cache repeat answers
Embedding API (one-time per chunk + per query) ~10-20% Batch; cache; use cheaper models where quality allows
Reranker calls (per query) ~5-10% Self-host BGE-reranker if Cohere is too expensive; ZeroEntropy zerank-2 (~40× cheaper)
Vector DB hosting ~5-15% pgvector or Qdrant cheaper than Pinecone; right-size replicas
Advanced technique LLM calls (HyDE, decomposition, query rewriting) Variable — 0-30% Use cheap models (Haiku, Gemini Flash) for these auxiliary calls

The Top Cost-Saving Techniques

  • Prompt caching — for repeated system prompts (common in chat use cases), Anthropic / OpenAI / Gemini all support caching with 50-90% discount on cached tokens
  • Right-size your LLM — most BFSI Q&A doesn't need Opus-tier. Sonnet 4.5 / GPT-4o / Gemini 2.5 Pro handle 90% of queries; reserve top-tier for hard cases (use Adaptive RAG to route)
  • Smaller embedding models for high-volume — text-embedding-3-small (1536) is often as good as -large (3072) for retrieval, 2× cheaper to index + store
  • Answer caching — for FAQ-style traffic, cache (query → answer); invalidate on KB update
  • Cheap auxiliary LLM — for HyDE, query rewriting, classification, judging — use Haiku / GPT-4o-mini / Gemini Flash. Save Opus / GPT-4.5 for the final generation.
  • Self-hosted rerankers at scale — BGE-reranker-v2-m3 on your own GPU may cost less than per-query API at millions of QPS

The Most Common Cost Mistake

Teams optimize the vector DB to save $100/month while ignoring the LLM that costs $5000/month. Always measure where money actually goes before optimizing.

🎯Key Takeaways

About Architecture

  1. RAG is 8 steps — load, chunk, embed, index (offline) + embed query, retrieve, augment, generate (online). Master each step.
  2. Retrieval quality is the #1 lever. Most failed RAG projects fail at retrieval, not generation. Spend 80% of effort there.
  3. Production retrieval = hybrid + RRF + rerank. This pipeline alone is 30-50% better than naive top-K vector search.

About Frameworks

  1. LlamaIndex for RAG-centric; LangGraph for agentic; Haystack for regulated. Pick based on the problem, not the popularity.
  2. The "use both" pattern (LlamaIndex + LangGraph) is the 2026 production default for systems needing both deep retrieval AND orchestration.

About Evaluation

  1. BLEU/ROUGE are wrong for RAG. Use faithfulness, answer relevancy, context precision/recall.
  2. RAGAS for metrics, DeepEval for CI/CD gates, TruLens for dashboards — or pick one and stick with it.
  3. Production thresholds (0.8 / 0.75) are heuristics, not absolutes. Calibrate to your use case: compliance bots need 0.92+, internal helpdesks can run at 0.75.
  4. Lock your LLM judge. Spot-check against human labels quarterly.

About Advanced Techniques

  1. Add complexity reluctantly. Start with hybrid + rerank; only add more when you've diagnosed a specific failure.
  2. Contextual Retrieval (Anthropic, Sept 2024) is the highest-impact "single recipe" — 67% retrieval failure reduction when stacked with reranker.
  3. GraphRAG, RAPTOR, agentic patterns are powerful but expensive — best for static KBs and high-value queries.

The discipline that separates working RAG from failed RAG: measure first, then optimize the right thing.
