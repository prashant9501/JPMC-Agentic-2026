The Technical Architecture and Developer Toolkit

⚙️MCP Architecture: The 3 Key Roles

MCP's design is a client-server model with three distinct roles in its architecture:

1. 🖥️ Hosts

The user-facing AI application - the "brain" of the operation that houses the AI model.

Examples: Claude Desktop app, IDEs like Cursor, or custom-built AI agents

2. 🔌 Clients

Live inside the Host application - small connectors that manage 1:1 connections to MCP servers.

Function: The Host spins up multiple Clients, one for each tool it needs to connect to

3. 🛠️ Servers

The external program that does the work - a wrapper built around external systems that "speaks" MCP.

Capabilities: Exposes Tools, Resources, and Prompts that Clients can discover and use

Examples: GitHub API wrapper, Postgres database connector

Key Separation: The Host orchestrates the AI, while the Clients and Servers handle the data and tool communication.

🌊The Communication Flow: Step-by-Step

When you use an MCP-enabled application, a specific sequence of events happens in the background. This communication is handled using JSON-RPC 2.0, a battle-tested protocol.

1️⃣ Initialization

The Host (e.g., your IDE) starts up. It launches its built-in Clients, which find and connect to MCP Servers (e.g., "Git" and "Filesystem" servers). They perform a handshake, exchanging capabilities and protocol versions.

2️⃣ Discovery

The Clients ask each Server, "What can you do?" The Servers respond with a detailed list of all the Tools, Resources, and Prompts they offer, including descriptions and required inputs.

3️⃣ Context Provision

The Host application now knows all available capabilities. It makes Resources (like files) available to the AI as context and parses the Tools into a format the LLM understands (like a JSON function-calling schema).

4️⃣ Invocation

The user gives a prompt (e.g., "Summarize the changes in the last commit"). The LLM determines it needs to use the git.get_last_commit_diff tool. The Host instructs the Git Client to invoke this tool. The Client sends the formal request to the Git Server.

5️⃣ Execution

The Git Server receives the JSON-RPC request. It executes its own internal logic—in this case, running the git diff HEAD~1 HEAD command on the command line.

6️⃣ Response

The Server gets the raw text from Git, packages it into a JSON-RPC response, and sends it back to the Client. The Client passes it to the Host, which injects the text into the LLM's context. The LLM then uses this context to write a natural language summary for the user.

🔌Transport Mechanisms: How Clients and Servers Talk

MCP is flexible and doesn't lock you into one type of network connection. It defines two main "transports" for how Clients and Servers exchange JSON-RPC messages.

1. Standard Input/Output (stdio)

How it works:

The Client launches the Server as a subprocess on the same machine. It sends messages directly to the server's stdin (standard input) and reads responses from its stdout (standard output).

Best for:

Local integrations, like IDE plugins. Perfect for git or filesystem servers running on your laptop.

Advantages:

  • Extremely Low Latency: No network overhead
  • Highly Secure: No network ports exposed, inherently safer

2. Streamable HTTP (and HTTP+SSE)

How it works:

The method for remote, network-based connections. The Server operates as a standalone web server. The latest specification, Streamable HTTP, uses HTTP POST/GET requests for communication, with an option to upgrade to Server-Sent Events (SSE) for real-time, streaming messages from the server.

Best for:

Cloud-based deployments, web applications, and any multi-client scenario where one central server (e.g., "Stripe" or "Salesforce" server) needs to serve many users.

Security:

Requires standard web security, including validating headers and implementing proper authentication (like OAuth 2.1) to secure the remote server.

The Ecosystem, Use Cases, and Future

🤝MCP vs. Frameworks (LangChain, LangGraph)

A common point of confusion is how MCP relates to agent frameworks like LangChain and LangGraph. The answer is simple:

They are NOT competitors; they are COMPLEMENTARY tools that solve different problems.

🏭 LangChain/LangGraph

Frameworks

Think of them as the "factory" or the "assembly line" for building an AI agent.

They provide:

  • Structure for agent's internal logic
  • Managing state
  • Chaining prompts
  • Handling memory
  • Orchestrating multi-step workflows
  • Enabling conditional logic (if X, then do Y)

They are the "brain" of the agent

⚡

🔌 MCP

Protocol

Think of it as the "standard power socket" or "USB port" for the factory.

It provides:

  • Standardized connections to outside world
  • Consistent way to access tools
  • Plug-and-play integration
  • Data and tool communication
  • Doesn't care about internal agent logic

It provides the "arms and legs" for the agent

How They Work Together:

You would use LangGraph to design your agent's complex, multi-step reasoning process. Then, within that agent's workflow, you would have it call MCP servers as its "tools."

LangGraph manages the agent's state and logic, while MCP handles the standardized, "plug-and-play" integration with GitHub, Slack, or any other external system.

A support agent can provide context-aware responses by pulling from CRM systems, order histories, and product databases, all through separate, standardized MCP connections.

🛡️Security and Future Evolution

As a protocol for connecting AI to real-world actions and data, security is paramount.

Security Considerations

The protocol is actively evolving to address security challenges. This includes:

  • OAuth 2.1 Authentication: Mandates for remote servers to ensure secure connections
  • Prompt Injection Prevention: Annotations to prevent malicious prompt manipulation
  • "Lookalike" Tool Protection: Safeguards to stop fake tools from tricking AI systems
  • Permission Management: Granular control over what actions AI agents can perform

The Future of MCP

MCP is a living protocol maintained on GitHub. Its evolution is focused on:

1. Better Security

Continuously hardening the protocol with enhanced authentication, authorization, and audit mechanisms.

2. Richer Context

Adding annotations so an AI can understand a tool's characteristics:

  • "This action is read-only" vs. "This action is destructive"
  • Cost implications of tool usage
  • Performance characteristics

3. Broader Language Support

Expanding the list of official SDKs, with languages like Rust as potential future targets, plus continued community growth.
