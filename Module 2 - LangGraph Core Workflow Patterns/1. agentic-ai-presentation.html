🧭Part 1

Workflows vs Agents vs Agentic AI

🤔Three Terms, Endless Confusion

"AI workflow", "AI agent", and "agentic AI" get used interchangeably in vendor decks — but they describe genuinely different levels of autonomy. Getting this wrong leads to over-engineering simple tasks, or trusting a brittle pipeline with a job that needs judgment.

The single question that separates them:
"Who decides what happens next — the developer, or the model?"

As we move from workflow → agent → agentic, the model takes over progressively more of the "what next" decision. More autonomy means more flexibility — and more need for guardrails.

🚦AI Workflow — The Fixed Recipe

An AI workflow is a predetermined sequence of steps designed by a developer. An LLM may sit inside one or more steps (to classify, extract, or summarise), but it does not choose the path — the path is hard-coded.

🍳 Analogy: following a recipe

A recipe lists exact steps in exact order. You don't decide whether to bake before mixing — the sequence is fixed. The cook (LLM) executes a step well, but never re-plans the meal.

BFSI use case — Loan-document intake pipeline

PDF arrives → OCR → LLM classifies document type → LLM extracts fields → validation rules → write to core system. Same path, every time. Predictable, auditable, easy to certify for compliance.

Best when: the process is well-understood, repeatable, and you value predictability over flexibility.

🧠AI Agent — Goal + Autonomy

An AI agent is given a goal and a set of tools, and the LLM decides — step by step — which tool to call, in what order, and when the goal is met. The path is discovered at run-time, not predetermined.

👩‍💼 Analogy: a capable junior analyst

You say "find out why Q3 churn rose." They decide what to query, which report to pull, whether to dig deeper — looping until they can answer. You set the goal; they choose the route.

BFSI use case — Dispute-resolution agent

Goal: "resolve this chargeback." The agent looks up the transaction, checks policy, queries the merchant record, decides whether to refund or escalate — choosing its own sequence of tool calls for each unique case.

Best when: inputs vary, the path can't be fully pre-scripted, and judgement adds value.

🏢Agentic AI — A Coordinated System

Agentic AI is the broader paradigm: multiple agents (and tools, and humans) coordinating toward a goal. Work is decomposed, delegated to specialists, and the results are synthesised — often with an orchestrator agent in charge.

🏬 Analogy: a whole department

A manager breaks a project into tasks, hands them to specialists (research, legal, finance), reviews their output, and assembles the deliverable. No single person does it all — coordination is the point.

BFSI use case — Investment research desk

A supervisor agent dispatches a market-data agent, a filings-RAG agent, and a risk agent in parallel; a writer agent drafts the memo; a reviewer agent checks it. The system, not any one agent, produces the result.

Best when: the problem is large enough to benefit from specialisation, parallelism, and review loops.

⚖️Seeing the Difference

The three paradigms placed side by side so the jump in autonomy is visual. Read it left → right: control over "what happens next" shifts from the developer, to a single model, to a coordinating system of models.

🔎 How to read it

  • Left (blue): the path is fixed rails the developer wired up — the LLM only fills in individual steps.
  • Middle (purple): one LLM sits at the centre, picks which tool to call, and loops until the goal is met — the rails are gone.
  • Right (green): an orchestrator delegates to specialist agents and a reviewer checks the result — no single agent owns the whole job.

What to infer: autonomy grows left → right, buying flexibility but costing predictability. Match the paradigm to the task — don't reach for the most autonomous option by default.

⚠️ Rule of thumb

Don't reach for agents when a workflow will do. Autonomy is a cost (latency, tokens, unpredictability), not a free upgrade. Earn it with a problem that actually needs it.

🔍Part 2

Agentic RAG

🆚Naive RAG vs Agentic RAG

Classic RAG is a workflow: embed the query → fetch top-k chunks → stuff into the prompt → generate. It works for simple Q&A but can't reason — it never asks whether the retrieved context is actually relevant, sufficient, or from the right source.

Naive RAG (fixed pipeline)

  • One retrieval, one source
  • No relevance check
  • Can't re-query or rephrase
  • Hallucinates when context is thin

Agentic RAG (agent decides)

  • Routes to the right source(s)
  • Grades relevance; rewrites query
  • Multi-step, multi-source retrieval
  • Reflects and self-corrects before answering

The shift: retrieval becomes a tool the agent chooses to use — possibly several times, from several sources — rather than a fixed first step.

🏛️Agentic RAG Architecture

The control flow of an agentic RAG system. Where naive RAG is a straight line (embed → fetch → answer), here retrieval is a decision the agent makes — possibly several times, across several sources — gated by quality checks and self-correction loops.

🔎 How to read it

  • The Router/Planner (purple) decides which source(s) to query for this question — not always all of them.
  • Green boxes are retrieval tools (vector DB, SQL, web) the agent uses as needed.
  • The orange Grade node asks "relevant & sufficient?"; the dashed orange arrows are the self-correction loops — rewrite & re-retrieve, or regenerate if the answer isn't grounded.

What to infer: the loops are the whole point — they stop the system answering confidently from weak context. Each loop costs latency and tokens, so cap the retries in code.

💰Use Case — A Financial Analyst Agent

Question from a relationship manager: "Is Meridian Wealth's exposure to renewable-energy bonds rising, and what do our latest research notes say about the sector?" A naive RAG bot fails — this needs two different data shapes and a judgement call.

1 · Route

Agent recognises a structured part ("exposure trend") and an unstructured part ("research notes"), and plans two retrievals.

2 · Retrieve (multi-source)

Queries the SQL holdings table for the bond exposure time-series; runs semantic search over the research-note vector store; falls back to web search for sector context.

3 · Grade & loop

If the notes are stale or off-topic, it rewrites the query and retrieves again — instead of answering from weak context.

4 · Synthesise & verify

Combines the trend + the qualitative view, checks every claim is grounded in retrieved evidence, then answers with citations.

This is exactly the architecture pattern behind production "analyst copilots" — a ReAct agent over SQL + a vector store + web search.

🧬Part 3

What Is an AI Agent?

✨Characteristics of an Agent

Not every LLM call is an agent. An agent exhibits a recognisable set of properties — the more of these are present, the more "agentic" the system:

🕹️ Autonomy

Decides its own next step toward the goal without being told the exact sequence.

🎯 Goal-directed

Works toward an objective, not a single fixed output. Knows when it's "done."

👂 Reactivity

Observes the result of each action and adapts the plan to what it learns.

🔧 Tool use

Acts on the world — calls APIs, queries data, runs code, browses.

🧠 Statefulness

Carries memory across steps — what it tried, what worked, what's left.

🔁 Persistence

Keeps looping (think → act → observe) until the goal is met or a limit is hit.

🧱The Three Components of an Agent

Strip an agent down and exactly three parts remain. Remove any one and it stops being an agent. The prompt isn't a fourth part — it's how you configure the Brain.

🔎 How to read it

  • ① The Brain (LLM): does the reasoning and decides the next step. Its behaviour is shaped by the prompt (role, task, context, constraints) — which is configuration, not a separate part.
  • ② Tools: how the agent acts on the world. Without them it can only produce text.
  • ③ Orchestration loop: feeds each tool result back to the brain so it can decide again — think → act → observe, repeated until done.

What to infer: this is exactly why a clever prompt alone isn't an agent (next slide). The brain reasons, the tools act, and the loop is the wiring that makes them an agent rather than a one-shot chatbot.

🐯No Tools, No Loop = A Toothless Tiger

The LLM and the prompt alone can talk about doing something. But without tools (to act) and an orchestration loop (to act repeatedly and react), the "agent" can't change anything in the real world. It collapses back into a glorified single-shot text generator.

🤔 So what actually turns an LLM into an agent?
Click to reveal ↓

Two things the LLM-plus-prompt lacks: (1) tools — the ability to act beyond emitting text; and (2) the orchestration/execution loop — the harness that feeds tool results back in and lets the model decide its next move. Take either away and you're left with a standard AI workflow, not an agent.

⚠️ The trap

A beautifully written system prompt with no tools and no loop is not an agent — it's a chatbot. Many "agent" demos are really just one LLM call dressed up. The teeth are the tools; the bite is the loop.

✅ The litmus test

Can it do something (call a tool) and then decide what to do next based on the result? If yes → agent. If it just answers once → workflow.

🛠️Part 5

Orchestration Frameworks & Vendor SDKs

🧰Four Frameworks You'll Meet

🔗 LangChain

The foundational toolkit: model wrappers, prompt templates, tools, memory, and "chains." Great for composing single-agent apps and RAG; the base layer the others build on or interoperate with.

🕸️ LangGraph

Graph-based orchestration for stateful, cyclic, multi-agent workflows. Nodes = functions/agents, edges = transitions. Built-in checkpointing, human-in-the-loop, and explicit control flow. The production workhorse for complex agentic systems.

👥 CrewAI

Role-based abstraction: define Agents (with a role, goal, backstory), give them Tasks, and run them as a Crew under a Process. Fast to express "a team of specialists."

🏢 Microsoft Agent Framework (MAF)

The merger of Semantic Kernel + AutoGen into one enterprise SDK (Python & .NET). Reached 1.0 / production in April 2026. Ships orchestration patterns, MCP + A2A support, and durable workflows. AutoGen is now maintenance-mode; MAF is the successor.

📎 Sources: langchain-ai.github.io/langgraph · docs.crewai.com · learn.microsoft.com — Agent Framework

🧠Pick by Mental Model, Not Star Count

Each framework is best understood by the shape of computation it makes natural. This gives you the one-glance mental model for each — choose by which shape fits your problem, not by GitHub popularity.

🔎 How to read it

  • LangChain = a chain: steps composed in a line. Best for linear single-agent apps and RAG.
  • LangGraph = a graph / state machine: nodes, branches, and cycles over shared state. Best for complex, stateful, multi-step control flow.
  • CrewAI = a crew: role-based agents run under a process. Best for "a team of specialists."
  • MAF & vendor SDKs = handoff: delegation is the core primitive — one agent passes control to another.

What to infer: these shapes aren't exclusive — real systems mix them (e.g., a CrewAI crew inside a LangGraph node). Pick the primary shape that matches your dominant control-flow need.

🏗️The Lab-Backed SDKs

Every major lab now ships an agent SDK. They look similar but make fundamentally different architectural bets — and that bet shapes your model lock-in, deployment, and debugging story.

🟣 OpenAI Agents SDK

Production successor to the experimental Swarm (Mar 2025). Mental model: handoffs. Primitives: Agents, Handoffs, Guardrails, Tracing/Sessions.

🔵 Google ADK

Agent Development Kit — a framework for orchestrating hierarchical agent trees, built for scale, strict IAM, audit logging; deep Vertex AI / Gemini integration (also runs Claude).

🟢 Anthropic Claude Agent SDK

Grew out of Claude Code. Philosophy: "give the agent a computer" — native bash, file system, deepest MCP integration, sub-agents & hooks. A local autonomous runtime.

One-liner: OpenAI = cleanest handoff model · Google ADK = enterprise orchestration platform · Claude SDK = autonomous computer-using runtime. They're often combined — e.g., Claude as the reasoning layer inside ADK or LangGraph.

📎 Sources: openai.github.io/openai-agents-python · adk.dev · docs.claude.com — Claude Agent SDK

🎼Part 6

Multi-Agent Design Patterns

🌳LangGraph — Choosing a Topology

LangGraph's power is that it makes the control flow explicit. Before writing a graph, run the task through this decision tree:

  • Linear task? → Pipeline (a simple chain of nodes).
  • Needs dynamic routing? → Router / Supervisor (a node decides who runs next).
  • Independent sub-tasks to fan out? → Parallel via the Send API (scatter-gather).
  • Quality needs iterative refinement? → Reflection or Evaluator–Optimizer loop.
  • Complex multi-step planning? → Planner / Plan-and-Execute.
  • A risky / destructive action? → Human-in-the-loop via interrupt().
  • Scaling to 6+ workers? → Hierarchical (teams of supervisors).

⚠️ Production lesson

Put stop conditions and iteration caps in code, not in the prompt. A reflection/supervisor loop with its stop condition only described in the system prompt can spin for dozens of iterations and quietly burn your token budget.

📎 Sources: langchain-ai.github.io/langgraph · reference.langchain.com — langgraph-supervisor

🕸️Supervisor + Parallel (Send API)

Three LangGraph patterns composed into one graph — the common shape of a production multi-agent system. It shows dynamic routing, parallel fan-out, and a human checkpoint working together.

🔎 How to read it

  • The Supervisor (purple, top) routes work to the right worker and collects their reports (dashed return arrow) — dynamic routing, not a fixed order.
  • From the Research worker, the Send API fans one step out into parallel sub-tasks (green) that are then gathered/reduced (orange) — classic scatter-gather for independent work.
  • The pink interrupt() box on the Writer is human-in-the-loop: the graph pauses for approval, then resumes.

What to infer: patterns compose. A real graph layers routing + parallelism + a human checkpoint — and the guardrails (iteration caps, the interrupt) live in the graph's code, not the prompt.

🧩LangGraph Patterns — In Detail

Router

A node inspects the state and conditionally directs flow to one of several downstream nodes (via conditional edges or Command(goto=...)). The classic "classify-then-dispatch": e.g., route a customer query to billing vs. tech vs. account nodes.

Parallel (Send API / scatter-gather)

The Send mechanism dispatches multiple branches simultaneously, each with its own slice of state; results merge downstream via a reducer. Use for "run the same step over N items" or independent multi-source retrieval. Beware race conditions on shared state.

Human-in-the-loop (HITL)

Call interrupt() to pause the graph at a checkpoint; a human reviews/approves; resume with the same thread_id and an updated state. Essential for destructive or high-stakes actions — the LLM suggests, the human authorises, the code enforces.

Reflection

A structured feedback loop: a generator produces output, a critic evaluates it, and the graph routes back for revision until a quality threshold is met. Improves reliability and reduces hallucination — at the cost of extra LLM calls (so cap the iterations).

Evaluator–Optimizer

A specialised reflection variant: one agent optimises (drafts/improves), a separate evaluator scores against explicit criteria, and the loop continues until the score passes. Great for content quality, code, or anything with a measurable rubric.

Planner / Supervisor–Worker

A supervisor (or planner) decomposes the goal and delegates sub-tasks to specialised worker agents, each with its own scratchpad, then synthesises the results. Scales to hierarchical teams (supervisors of supervisors) for large workloads.

📎 Source: langchain-ai.github.io/langgraph — multi-agent concepts

👥CrewAI — Sequential vs Hierarchical Process

In CrewAI you define role-based Agents and assign them Tasks; a Crew runs them under a chosen Process. Two core processes:

Sequential Process

Tasks run in a fixed order; each task's output becomes context for the next. Simple, predictable, easy to reason about.

Example: Researcher → Analyst → Writer producing a market brief, passing work down the line.

Hierarchical Process

A manager agent (auto-created or specified) plans, delegates tasks to the right worker agents, validates their output, and decides what's next.

Example: a manager dynamically assigns sub-questions to specialists and assembles the final answer.

Rule of thumb: Sequential when the pipeline is known and stable; Hierarchical when task assignment should be decided at run-time by a coordinating agent.

📎 Source: docs.crewai.com — Processes

🔀CrewAI Processes — Visualised

The same three agents, two different processes — contrasting how CrewAI coordinates a team when the plan is fixed versus when it should be decided at run-time.

🔎 How to read it

  • Left — Sequential: a fixed pipeline where each agent's output becomes the next agent's context. Predictable and easy to debug.
  • Right — Hierarchical: a manager agent plans, delegates to the right workers, validates their output (dashed loop), and decides what happens next.

What to infer: choose Sequential when the order is known and stable; choose Hierarchical when task assignment genuinely needs run-time judgement. Hierarchical is more flexible but adds the manager's extra LLM calls and less determinism.

🤝Microsoft Agent Framework — Handoff & Delegate

MAF ships a workflow engine with several orchestration patterns out of the box. The handoff pattern is the multi-agent delegation primitive:

Handoff (delegate)

A router agent reads the conversation and decides which specialist agent should handle the next turn — then hands control over (with optional backtracking). E.g., a triage agent routing to Sales, Support, or Billing agents.

Also available: Sequential · Concurrent (fan-out/fan-in) · Group chat · Magentic

Sequential runs agents in order; Concurrent runs them in parallel and aggregates; Group chat lets agents converse; Magentic (from Magentic-One) handles open-ended planning. All support streaming, checkpointing, and human-in-the-loop.

Why it matters: MAF unifies AutoGen's multi-agent ideas with Semantic Kernel's enterprise foundations (state, type-safety, telemetry) — and patterns are composable (a concurrent step can contain sequential sub-chains).

📎 Sources: learn.microsoft.com — Agent Framework overview · devblogs.microsoft.com — MAF 1.0

🐝OpenAI — The Swarm (Handoff) Pattern

OpenAI's Swarm (Oct 2024) distilled multi-agent orchestration to two ideas: an agent is instructions + tools, and a handoff is a tool that returns another agent. That elegant minimalism is why it's still the best teaching model — even though it's now archived.

Swarm (educational, archived)

  • <1000 lines; stateless
  • Agent + functions; handoff = function → agent
  • README now redirects to the Agents SDK

Agents SDK (production successor)

  • Same handoff mental model
  • Adds Guardrails, Tracing, Sessions
  • Responses API tools; actively maintained

⚠️ Don't build new systems on Swarm

Use it to understand the swarm/handoff pattern, then build on the Agents SDK, which keeps the identical primitives but is production-ready.

📎 Sources: github.com/openai/swarm (archived) · openai.github.io/openai-agents-python

🔁The Handoff in Action

A single user request traced through a handoff-based system — the pattern shared by OpenAI Swarm/Agents SDK, Microsoft Agent Framework, Google ADK, and Claude sub-agents.

🔎 How to read it

  • The Triage agent (purple) doesn't answer — it classifies the request and hands off to the right specialist. A handoff is literally "return another agent."
  • Each specialist (green) owns its domain and uses its own tools (orange) to act → observe → respond.

What to infer: the triage agent stays small and cheap; expertise and tools live in the specialists. This keeps each agent's prompt focused and lets you add a new specialist without touching the others.

The same primitive underlies MAF handoff, Google ADK delegation, and Claude SDK sub-agents — different syntax, one idea: delegate to a specialist.

🎯Key Takeaways

  • It's a spectrum: workflow → agent → agentic system. The dividing line is who decides what happens next.
  • Tools + the loop make the agent. An LLM with a great prompt but no tools and no orchestration is a chatbot — a toothless tiger.
  • Agentic RAG beats naive RAG by making retrieval a tool the agent routes, grades, and loops over — not a fixed first step.
  • The business impact is real but uneven. JPMorgan, Morgan Stanley, Klarna, and UiPath show big wins on high-volume, well-scoped tasks — and the honest lesson (Klarna) is to keep humans for nuance and measure CSAT/ROI, not just deflection.
  • Pick frameworks by mental model: LangChain (chain) · LangGraph (graph/state) · CrewAI (roles) · MAF / vendor SDKs (handoff). MAF = SK + AutoGen, GA 2026; OpenAI Swarm → Agents SDK.
  • Patterns repeat across frameworks: router, parallel, reflection, planner/supervisor, and handoff show up everywhere — learn the patterns, not just one API.
  • Put guardrails in code: iteration caps, stop conditions, and human-in-the-loop belong in the harness, not the prompt.
